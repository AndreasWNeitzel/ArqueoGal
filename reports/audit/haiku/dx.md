# Developer Experience Audit — ArqueoGal (2026-04-26)

## Summary

ArqueoGal has solid foundational practices but exhibits four significant friction points that compound during active development: (1) no unified entry-point script ("make it work") for a fresh clone, forcing manual discovery of `rapidsenv` activation and multi-step feature-build pipelines; (2) missing pre-commit hooks and git discipline enforcement despite CLAUDE.md requirements; (3) test suite has a collection-blocking polars import error and 873 tests with slow inner-loop patterns (no `--dry-run` modes, no profiling output); (4) gallery rebuild requires manual knowledge of which scripts produce which PNG files, with no centralized orchestration. All paths are relative, which works but requires terminal-to-repo navigation.

## Detailed Findings

### 1. Environment Activation and Entry Points

**Finding**: The project requires activation of `~/.venvs/rapids25.10_python3.12_cuda13/` via the `rapidsenv` shell alias, but this is documented only in CLAUDE.md and README.md (§Environment), never executed automatically.

- `rapidsenv` is defined in `~/.bashrc` (not in the repo), pointing to a WSL-specific venv location
- A new developer cloning the repo sees `pyproject.toml` (which declares setuptools but provides only runtime-docs dependencies, not executable install)
- No `setup.sh` or `just` target; no `.venv` symlink; no automatic activation on `cd` (e.g., direnv, pyenv-virtualenv, or a startup hook)
- The README states "Activate with `rapidsenv` (shell alias). Do not create new venvs" but provides no entry script that executes this step

**Consequence**: Clone → 2–3 minutes debugging why imports fail before discovering the alias; test runs fail silently if the alias is not activated; new developers miss RAPIDS-pin constraints entirely.

### 2. Git Discipline and Pre-commit Hooks

**Finding**: CLAUDE.md §3 (hard invariant 3) forbids `main` ↔ `experimental` cross-imports, §1 forbids unvetted commits, and §14 mandates provenance sidecars on every Parquet. None of these are enforced at the git level.

- `.git/hooks/` contains only sample templates; no working hooks exist
- No `.pre-commit-config.yaml` to gate commits on ruff format/lint, provenance JSON validation, or cross-import scanning
- The repo does run ruff on CI-equivalent (via pytest), but pre-commit would catch style drift locally, 15 seconds into an edit
- DESIGN.md co-commit discipline (§15 in CLAUDE.md hard rules) is manual code review only

**Consequence**: A developer can commit malformed JSON sidecars, introduce a main ↔ experimental import, or merge unformatted code without friction; corrections happen downstream after git push, requiring team coordination.

### 3. Test Suite Defects and Slow Inner Loop

**Finding**: Test collection fails due to missing `polars` in the rapids venv, and test execution patterns lack performance instrumentation.

- `tests/data/test_ir_photometry.py:16` imports `polars` but the dependency is not in `pyproject.toml` dev group (line 55–65)
- 873 tests pass collection after the import error is resolved, but no test runs `--durations=N` or `pytest-benchmark` to surface slow tests
- Long-running ingestion scripts (`scripts/build_pipeline1_features_stream*.py` — each 20+ KB) lack `--dry-run` flags; dry-run simulation is only in notes, not in the code
- No integration-test smoke test runs automatically (Aim smoke test at `scripts/aim_smoke_test.py` is 1.4 KB but is never invoked by CI or pre-commit)

**Consequence**: A test run that should take 10 seconds can hang on slow tests silently; feature refactoring requires manual trial-and-error to ensure downstream script compatibility; no dashboard or artifact to track regression.

### 4. Gallery Rebuild and Orchestration

**Finding**: 197 PNG files in `reports/gallery/` and `reports/figures/` are generated by scattered, untracked entry points (e.g., `scripts/build_pipeline1_features_stream*.py` emits stage-A features, then separate scripts emit Hermite reprojections, then yet other scripts render the gallery). No centralized `make figures` or `gallery rebuild` target.

- `scripts/` contains 26 KB of Python entry points, but no script lists which scripts must run in which order to regenerate the gallery
- No `Makefile`, `justfile`, or `dvc.yaml` to orchestrate stages (raw data → interim → processed features → predictions → gallery)
- The README points to `reports/figures/data_overview/` as the "canonical overview," but no section explains how to regenerate it after a data-acquisition change
- Gallery is gitignored (`.gitignore`: `reports/figures/**/*.pdf`), but PNG files are committed; unclear which figures are source-of-truth

**Consequence**: Reproducing the gallery after a pipeline change requires reading through 20+ scripts and docs to infer the correct order; a new contributor cannot reliably regenerate figures; no CI verifies that the committed gallery matches the current code.

### 5. Path Management and Reproducibility

**Finding**: All entry-point scripts use relative paths or `Path(__file__).resolve().parent.parent` anchors, which works but requires the terminal to be in the repo root or requires Python to be run with explicit `PYTHONPATH=src` (as shown in `run_pipeline1_inference.py` CLI docstring, line 112).

- `PYTHONPATH=src python scripts/run_pipeline1_inference.py` is the documented invocation (README doesn't mention this; see script docstring only)
- Absolute paths are not used consistently; some scripts assume `data/processed/` exists relative to `Path(__file__).parent.parent`
- A developer running a script from outside the repo root will get `FileNotFoundError` or import errors

**Consequence**: Scripts are not easily callable from a monorepo parent or CI environment; tooling integration requires wrapper scripts or path gymnastics.

### 6. Dependencies and Version Pinning

**Finding**: `pyproject.toml` declares runtime dependencies as "for documentation only" (line 16–21), with the real environment managed externally via the rapids venv. This is correct per CLAUDE.md, but it creates an audit blind spot.

- A new developer cannot run `uv sync` or `pip install -e .` to get a working environment
- The rapids venv is not version-pinned in the repo; `uv.lock` exists (from recent commit 9a1b85c) but does not govern the production venv
- Polars (imported in test but missing) is not declared anywhere; it's an implicit dependency of a data-processing module

**Consequence**: Environment reproducibility is delegated to external documentation (HARDWARE_SETUP.md); a developer cannot reconstruct the rapids venv from the repo alone.

## Missing Tools

- **Pre-commit hook framework**: `.pre-commit-config.yaml` with stages for ruff, provenance JSON schema validation, and cross-import scanning
- **Task orchestrator**: Makefile or `justfile` defining `make test`, `make gallery`, `make lint`, `make ci` (or `just` equivalents)
- **Smoke-test automation**: A `.claude/commands/smoke` target or a pre-push hook that runs the Aim smoke test and a 100-row end-to-end pipeline test
- **Dry-run modes**: `--dry-run` / `--n-rows 100` flags on ingestion and feature-build scripts for fast iteration
- **Test timing dashboard**: `pytest --durations=10` output persisted to a JSON artifact for regression tracking

## Recommendations (Prioritized)

1. **Create `./.claude/commands/init.sh`**: Detects the missing rapids venv, sources the activation, validates paths, and prints next steps. Gate `make ci` / `just ci` on passing this check.

2. **Add `.pre-commit-config.yaml`**: Minimal hooks for ruff format/lint (existing CI behavior) plus a custom hook that validates provenance JSON schema on any `*.provenance.json` added to the staging area. Commit this before next pipeline run.

3. **Create `Makefile` targets**:
   - `make test`: run pytest with `--tb=short`
   - `make test-fast`: skip slow/gpu/stress tests
   - `make lint`: ruff check + format verify (as pre-commit would)
   - `make gallery`: echo which scripts need to run (document, don't automate yet)
   - `make ci`: run lint + fast tests + smoke test

4. **Fix the polars import**: Add polars to `pyproject.toml` dev group (if intentional) or remove the import from test_ir_photometry.py (if dead code).

5. **Add `--dry-run` to feature-build scripts**: Emit 100 rows + provenance to a test output, verify schema, quit. Enables fast inner-loop iteration.

6. **Document the inference CLI invocation**: Add a `.claude/commands/infer.sh` that wraps `scripts/run_pipeline1_inference.py` with proper PYTHONPATH and default paths, so the user can run `./infer.sh --input-parquet <path>` without reading the 1254-line script.

## Low-Friction Wins

- Add `# PYTHONPATH=src` comment to top of every `scripts/*.py` (currently only in docstrings)
- Create `.env.example` showing `GAIA_AIP_TOKEN=` and `ARQUEOGAL_CREDENTIALS_PATH=` (currently only in README)
- Add a "How to regenerate the gallery" section to README (currently missing)
- Create `tests/Makefile` or `.claude/commands/test` that activates the venv before running pytest

## Audit Caveats

- No evaluation of the scientific code itself (model training, abundance inference, bimodality detection); this audit is DX-only
- The Rapids venv may have additional local dependencies not captured in any artifact (e.g., cupy, cuml versions); recommend running `pip freeze > requirements-rapids-locked.txt` in the venv and committing it for reproducibility
- The test suite error collection time (17 seconds) is acceptable but could be reduced with pytest-xdist if tests are parallelizable (untested)
